# WP-08.5-04 — Completion Report

Broadcast-Style Live Scoreboards. Status: **done**.

## Repository findings

Checked the Objective's checklist ("full-screen mode, TV/LED layouts,
live indicators, provisional notices, last-updated time, Reverb updates,
polling fallback, and disconnected states") against the actual scoreboard
code (`resources/js/components/live-score-display.tsx`, its two
consumers `resources/js/pages/scoring/show.tsx` and
`resources/js/pages/public/scoreboard.tsx`) rather than assuming a rebuild
was needed. Most items were already real, built across two prior
sessions: full-screen mode, team logos, running clock, and boxing
corners (git history, `d824cc9`), plus `LiveBadge`/score-clock typography
(WP-08.5-02). Reverb updates (`useEcho`, operator console only) and the
5-second polling fallback (both pages, always-on baseline) were already
correctly wired, as was the disconnected-state banner
(`pollFailures >= 2`) and the public page's "provisional, not the
official result" notice.

Two real gaps, found by reading every consumer rather than trusting the
component alone:

1. Both pages' own breadcrumb-level "Live now" indicator — a separate bit
   of markup outside `LiveScoreDisplay` itself — was still the old plain
   `Badge variant="destructive"`, not the `LiveBadge` primitive
   WP-08.5-02 introduced. `LiveScoreDisplay`'s *internal* status badge
   already used `LiveBadge`; these two breadcrumb copies didn't, because
   they live in the page, not the shared component.
2. No "last updated" time existed anywhere — a real Objective item with
   zero prior implementation.

Two Objective items are **not built here**, both a considered scoping
call rather than an oversight (documented in
`docs/ui-ux/premium-design-system.md`'s new "WP-08.5-04" section):

- **TV/LED layouts** — this phase already has a dedicated WP for exactly
  this (WP-08.5-07), which the design-system doc's own "Large-display
  scaling" section (written by WP-08.5-02) already defers to by name.
  Building a kiosk/TV layout here would duplicate that WP's scope.
- **Athletics scoreboard** — re-confirmed it doesn't exist as live data
  anywhere in the app (no `ScoreboardType::Athletics` case, no
  scoring event ever attributes a time/mark to an individual athlete
  mid-race — the same finding WP-08-11 made originally). Inventing one
  here would mean hardcoding placeholder data, explicitly excluded by
  this WP's own rules.

## Files changed

- `resources/js/components/live-score-display.tsx` — new `LastUpdated`/
  `TickingLastUpdated` sub-components (same remount-a-ticker-from-zero
  technique as the existing `RunningClock`, so no render reads the wall
  clock directly) and a new optional `lastUpdatedAt` prop, rendered next
  to the full-screen button.
- `resources/js/pages/scoring/show.tsx` — new `lastUpdatedAt` state,
  bumped on every successful poll response and every Echo `score.updated`
  push, passed to `LiveScoreDisplay`; the breadcrumb "Live now" badge is
  now `LiveBadge`; the now-unused `Badge` import was removed.
- `resources/js/pages/public/scoreboard.tsx` — same `lastUpdatedAt`
  tracking (poll success only — no Echo channel for guests, unchanged)
  and the same `LiveBadge` swap for the breadcrumb; the separate
  "provisional, not the official result" `Badge` is untouched (`Badge`
  import stays, still used there).
- `docs/ui-ux/premium-design-system.md` — extended "Live indicators" with
  the breadcrumb-badge fix, added a new "Last-updated time" section, and
  a new "WP-08.5-04" section recording both the closed gaps and the two
  deliberately-deferred items.
- `docs/phases/phase-08-5-premium-sports-experience/CHECKLIST.md` —
  checked off WP-08.5-04.
- `docs/reports/phase-08-5/WP-08.5-04-completion.md` — new, this file.

No route, controller, model, migration, policy, or test fixture was
touched — this WP is frontend-only, matching its own scope (the
Objective is entirely about presentation of already-existing live data).

## Visual / backend / frontend changes

- Both the operator console and public scoreboard's breadcrumb area now
  shows the pulsing `LiveBadge` pill instead of a flat destructive badge
  when a session is active — visually consistent with every other "Live"
  mention in the app (`public/meet.tsx`'s live-now list, the board's own
  internal status indicator).
- Both pages now show "Updated just now" / "Updated Xs ago" next to the
  full-screen toggle, ticking up every second and resetting to "just
  now" on every real poll/Echo update. While disconnected, the figure
  keeps climbing instead of freezing or resetting — a second, honestly-
  worsening signal alongside the existing static warning banner.
- Backend: untouched. No PHP file was modified in this WP.

## Reusable components

No new component — `LastUpdated`/`TickingLastUpdated` are internal to
`live-score-display.tsx` (not exported), since both current consumers
already go through `LiveScoreDisplay` itself; a third consumer needing
the same ticking-timestamp pattern independently would be the trigger to
extract it, per this codebase's established "extract on second use"
convention.

## Motion

`TickingLastUpdated` re-renders once per second (a ticking counter, not
a CSS animation) — no new `prefers-reduced-motion` concern, since it's
plain text content changing, not a transition or animation the reduced-
motion reset would need to suppress. `LiveBadge`'s existing pulse
(WP-08.5-02) is unchanged by its new breadcrumb usages.

## Responsive behavior

The new `LastUpdated` text and the full-screen button share the existing
`flex items-center gap-3` row inside the already-responsive top bar — no
new breakpoint-specific behavior; verified by inspection that the text
wraps naturally at narrow widths within the existing `justify-between`
row (`flex-wrap` was not needed; the label is short enough — "Updated
Xs ago" — to sit alongside the button at every width already exercised).

## Large-display behavior

No kiosk/TV route was added (WP-08.5-07's scope, confirmed still true —
see "Repository findings"). The existing `fullscreen` mode's high-
contrast, content-driven size steps were re-checked against the new
`LastUpdated`/`LiveBadge` additions and read correctly at both size
steps; large-display views still carry zero private data and zero
operator controls (unchanged — no prop or route was added that could
weaken that boundary).

## Accessibility

- `LiveBadge`'s existing `aria-hidden` pulse dot is unchanged by its two
  new breadcrumb call sites — same component, same accessible behavior.
- `LastUpdated`/`TickingLastUpdated` render as plain visible text with no
  live-region wrapper; this is a secondary, glanceable freshness
  indicator, not an alert — a screen-reader user is not expected to have
  every second's tick announced, and the existing `disconnected` banner
  (already `role="status"`) remains the actual accessible signal for "the
  data may be stale."
- No heading order, focus-management, or form-label behavior was touched.

WP-08.5-09 concern, not this one's.
