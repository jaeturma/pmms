# WP-08.5-09 — Completion Report

Public Portal Performance and Accessibility Polish. Status: **done**.

## Repository findings

Checked every item in the Objective's list ("bundle usage, image
optimization, lazy loading, Reverb fallback, caching, keyboard support,
contrast, reduced motion, touch targets, privacy, graceful failures")
against the actual code and, where measurable, actual numbers — rather
than repeating prior WPs' unverified assumptions.

**The single biggest finding was correcting a running assumption, not
confirming a bug.** Every completion report from WP-08.5-02 through 08
flagged `wayfinder-*.js` (~346.8 kB / ~109.2 kB gzip) as "a bundle-size
concern, WP-08.5-09's problem to solve" — based on its name. Actually
opening the built chunk this WP found the bulk of it is `es-toolkit`
(a utility library), which is `@inertiajs/core`'s own internal
dependency, required by every Inertia page — admin or public — to run
Inertia itself. Confirmed via the build manifest that an admin page
(`dashboard.tsx`) and a public page (`public/home.tsx`) both depend on
the exact same chunk. This is correct, expected shared-chunk behavior:
the browser downloads it once per session and reuses it for every
subsequent page, admin or public. There's no real fix available here
without changing the Inertia version, which is out of scope. Closed the
flag with an honest "investigated, not actually a problem" rather than
carrying it forward again.

**One real, previously-uncaught performance bug, in this phase's own
code**: `PortalController::home()` was calling
`MedalTallyService::standings()` twice in a single request — once from
`currentLeaders()` (WP-08.5-03), once from `closingSummary()`
(WP-08.5-08), each independently re-querying and re-grouping validated
placements. Fixed by computing the district standings once in `home()`
and passing the resulting collection into both helpers.

**Contrast had never actually been measured anywhere in this project**
— every prior accessibility pass (including this doc's own WP-08-15
section) explicitly deferred it, reasoning "same tokens already in
place." This WP's own Objective names "contrast" directly, so it was
finally computed for real (OKLCH → linear sRGB → WCAG contrast ratio).
Two real failures found and fixed — see "Visual / backend / frontend
changes" below.

## Files changed

- `app/Http/Controllers/PortalController.php` — `home()` now computes
  the district standings once (`$districtStandings`, sorted by points)
  and passes it to `currentLeaders()`/`closingSummary()`, whose
  signatures changed from taking `MedalTallyService $tally` to taking
  the pre-computed `Collection` directly. No change to either method's
  output shape or the JSON payload — this is an internal efficiency fix,
  not a behavior change.
- `resources/js/components/live-score-display.tsx` — the disconnected-
  banner's message text no longer sets `text-warning` (measured
  ~2.1:1/~1.05:1 contrast failure, both light and dark mode considered);
  the icon keeps the warning color (decorative, `aria-hidden`).
- `resources/js/pages/public/tally.tsx` — the same fix on the kiosk
  connection-status banner (WP-08.5-07's own addition of this pattern).
- `resources/js/pages/public/home.tsx` — the closing-summary "Meet
  concluded" badge switched from `text-medal-gold` (measured ~1.89:1)
  to `bg-medal-gold text-medal-gold-foreground` (measured ~8.5:1), the
  same solid-fill pairing `RankBadge` already uses correctly.
- `resources/js/components/opening-countdown.tsx` — added a
  `Number.isNaN(target)` guard (graceful failure against a malformed
  `startsAt`, unreachable with real data today but cheap to harden);
  the ticking `setInterval` now clears itself once the target instant
  has passed, instead of continuing to tick forever while the parent
  keeps the component mounted.
- `docs/ui-ux/accessibility-review.md` — new "Color contrast audit"
  section with the real measured ratios for every color pairing this
  phase introduced or reused, the two fixes, and three admin-only
  instances of the same underlying bug flagged (not fixed — out of this
  WP's public-portal scope).
- `docs/public-portal.md` — updated the "Accepted deviations" note,
  which previously said contrast was "not re-audited," to point at the
  new audit instead.
- `docs/ui-ux/premium-design-system.md` — new "WP-08.5-09" section
  covering every Objective item, including the ones found already
  satisfied (image optimization, lazy loading, Reverb fallback, keyboard
  support, touch targets) and the ones deliberately not acted on
  (caching headers — no CDN/proxy in front of this single-machine
  deployment for them to guard against).
- `docs/phases/phase-08-5-premium-sports-experience/CHECKLIST.md` —
  checked off WP-08.5-09.
- `docs/reports/phase-08-5/WP-08.5-09-completion.md` — new, this file.

No new route, migration, authorization rule, or test fixture — every
change is either a controller-internal efficiency fix (identical output
shape, confirmed by the unchanged test suite) or a presentational
contrast/robustness fix.

## Visual / backend / frontend changes

- The scoreboard's and tally kiosk's "connection lost" banners now show
  their message in the ordinary (already-accessible) body text color
  instead of a warning hue that measured under WCAG AA in both light and
  dark themes — no visual regression in the everyday sense, since the
  color was already too close to invisible to read comfortably; this
  reads as *more* legible, not different.
- The home page's "Meet concluded" badge is now a solid gold pill with
  dark text (matching `RankBadge`'s rank-1 treatment) instead of pale
  gold text that was genuinely hard to read.
- `home()`'s response is unchanged in shape — only its internal query
  count dropped by one `MedalTallyService::standings()` call.
- `OpeningCountdown` behaves identically for every real scheduled match;
  the new guards only change behavior for inputs that can't occur with
  real data today.
