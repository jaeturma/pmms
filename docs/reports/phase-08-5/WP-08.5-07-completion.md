# WP-08.5-07 — Completion Report

Large Display LED Wall and Kiosk Modes. Status: **done**.

## Repository findings

Every prior WP in this phase had already deferred exactly this work to
WP-08.5-07 by name: WP-08.5-02's "Large-display scaling" section said
"no kiosk/TV route exists yet, WP-08.5-07's scope"; WP-08.5-04 scoped
"TV/LED layouts" out for the same reason; WP-08.5-06 re-confirmed it
again. Confirmed before building: no kiosk/TV route or layout existed
anywhere in the codebase. The two clearest, already-real-data-backed
candidates for a large-display mode are the live scoreboard
(`public/scoreboard.tsx`, which already has a `fullscreen` styling mode
from earlier WPs) and the medal tally (`public/tally.tsx`, which had no
comparable treatment at all).

Rather than a new dedicated route (a heavier, harder-to-justify change
for purely a presentational mode of already-public data), this WP adds
a `?kiosk=1` query flag to those two existing routes — same controller
action, same props, zero backend changes. Confirmed via
`@inertiajs/react`'s compiled source (not assumed) that Inertia's
`layout` resolver option receives both the page component name and the
full page object, which is what makes swapping to a chrome-free layout
based on a query flag possible without a new backend prop.

## Files changed

- `resources/js/app.tsx` — the `layout` resolver now checks
  `isKioskVisit(name, page.url)` (only for `public/scoreboard`/
  `public/tally`) before its existing name-based switch, returning the
  new `KioskLayout` when true.
- `resources/js/layouts/kiosk-layout.tsx` — new. A bare full-viewport
  shell with none of `PublicLayout`'s header, footer, sign-in/dashboard
  button, or bottom tab bar.
- `resources/js/hooks/use-kiosk-mode.ts` — new. `useKioskMode()`, the
  same `?kiosk=1` check as `app.tsx`'s resolver, usable inside page
  components via `usePage()`.
- `resources/js/components/live-score-display.tsx` — two new optional
  props: `showFullscreenToggle` (hides the manual toggle button) and
  `maxWidthClassName` (overrides the default `max-w-5xl` fullscreen
  cap, so kiosk mode can pass a much wider one).
- `resources/js/pages/public/scoreboard.tsx` — new kiosk render branch:
  no back-link/breadcrumb chrome, the board permanently at its largest
  size step (`fullscreen` forced true, not tied to the real browser
  Fullscreen API), no toggle button, a wider board cap
  (`max-w-[1600px]`), safe-margin padding (`p-6 sm:p-10 lg:p-16`). A new
  "Kiosk / TV mode" link (next to "Back to schedule") on the normal page
  makes the mode discoverable.
- `resources/js/pages/public/tally.tsx` — new kiosk render branch: no
  `PublicMeetNav`/filters/secondary sections, the full (untruncated)
  ranking table at larger text (`text-lg` on `<Table>` itself, inherited
  by every cell), a new 30-second `usePoll()` auto-refresh (this page had
  no polling before), a connection-status banner on repeated poll
  failures. Same "Kiosk / TV mode" link on the normal page, preserving
  whatever filter was active.
- `docs/ui-ux/premium-design-system.md` — new "WP-08.5-07" section
  covering the layout-resolution mechanism, both kiosk modes, and three
  explicit design decisions (why a query flag not a new route; why no
  fixed `aspect-ratio` box; why no private/admin data check was needed).
- `docs/phases/phase-08-5-premium-sports-experience/CHECKLIST.md` —
  checked off WP-08.5-07.
- `docs/reports/phase-08-5/WP-08.5-07-completion.md` — new, this file.

No route, controller, model, migration, policy, or test fixture was
touched — this WP is frontend-only, reusing the two existing public
controller actions unchanged.

## Visual / backend / frontend changes

- Visiting `/meets/{meet}/matches/{match}/scoreboard?kiosk=1` or
  `/meets/{meet}/tally?kiosk=1` now renders a chrome-free, large-text,
  auto-refreshing display suited to a TV/projector/LED wall/kiosk,
  reachable either by typing the URL or clicking the new "Kiosk / TV
  mode" link on either page's normal view.
- The normal (non-kiosk) scoreboard and tally pages are otherwise
  unchanged, aside from the new link.
- Backend: untouched. No PHP file was modified in this WP.

## Reusable components

- `KioskLayout` — available to any future page that needs the same
  chrome-free shell (e.g. if WP-08.5-08's event presentation work wants
  a large-display podium view).
- `useKioskMode()` — the one place the `?kiosk=1` check lives for page-
  level components; a third consumer would just call the same hook.
- `LiveScoreDisplay`'s new `showFullscreenToggle`/`maxWidthClassName`
  props are generically useful for any future caller that wants the
  big-board styling without the toggle button or the normal width cap.

## Motion

No new animation. The existing `LiveBadge` pulse and `RunningClock`/
`LastUpdated` ticking (both already reduced-motion-safe) render

`LiveScoreDisplay` component.

## Responsive behavior

Both kiosk views use responsive padding (`p-6 sm:p-10 lg:p-16`) so the
same route works reasonably from a tablet-sized kiosk panel up to a
large LED wall — verified by inspection of the padding/font-size scale
already established for the `fullscreen` mode elsewhere in this phase,
not a new pattern.

## Large-display behavior

This WP's entire subject. No fixed `aspect-ratio` box was used
deliberately — actual displays vary (16:10 projectors, portrait kiosk
panels), and forcing one would letterbox on anything else; "safe
margins" instead means generous responsive padding so content never
touches the frame edge, the broadcast "title-safe area" convention
without hardcoding a specific screen shape. Both kiosk views reuse the
exact same public-safe props the normal page already receives
(`Meet::published()`-scoped, no athlete photos, no operator controls) —
confirmed there was no new data to check, since nothing new was added to
either controller action.

## Accessibility

- The scoreboard kiosk view keeps every existing accessible behavior of
  `LiveScoreDisplay` unchanged (aria-live score region, aria-hidden
  decorative icons, etc.) — only the surrounding page chrome changed.
- The tally kiosk view's connection-status banner uses `role="status"`,
  the same convention the scoreboard's `disconnected` banner and
  `PublicLoadingSkeleton` (WP-08.5-06) already established.
- No heading order, focus-management, or form-label behavior was
  touched; both kiosk views keep a single `<h1>`.
